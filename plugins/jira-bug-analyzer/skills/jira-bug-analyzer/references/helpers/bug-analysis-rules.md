# Bug-analysis rules — reality-check + reproduce-first before diagnosing

The **maintainable** ruleset for HOW the analyzer investigates a bug (Golden Rule `[REPRO]`), applied at
**Phase 3** alongside the existing Fix-1…Fix-8 flow. The analyzer follows this at **Fix-5.5** (repro) and
carries the result into **Fix-6** (root cause) / **Fix-8** (approval) / the confidence scorecard.

> **How to maintain (this is the ONE place):** edit / add / remove rules here. Keep each a short, checkable
> imperative. Changes sync project↔user-scope and apply to every project the skill analyzes. Don't scatter
> analysis rules into the phase files — link back to a rule id (`A#`). Complements `fix-code-rules.md`
> (that governs *writing* the fix; this governs *diagnosing* it).

Foundation: **evidence over assumption.** A root cause without a confirmed (or strongly-evidenced) trigger is a
hypothesis, not a diagnosis — and you do not fix a hypothesis.

> **`[REPRO_ON]` conditional (default = SKIP on-device repro).** As of 2026-10-13, Fix-5.5 defaults to **A1–A3 only** (reality-check + static trace from media/code). **A4–A6 (on-device repro) and A8–A10 (can't-reproduce ladder) run only when `[REPRO_ON]=true`**, set by the `--repro` flag or NL intent in the user's request (see SKILL.md `[REPRO]` + the `Flags` section). When `[REPRO_ON]=false` the analyzer: skips device-lock acquisition in Phase 3, emits `Reproduced: skipped (no --repro)` + `not device-verified` flag in the Fix-6 block, scores `deterministic_repro=0` with `reason: no-repro-flag`, and under `--auto` the auto-approve threshold raises from 80 → 90 to compensate. A11–A15 (rigor) always apply.

## 1. Reality check — is this a real code bug?
- **A1** Before diagnosing, classify the ticket: **real app-code bug** vs a non-code cause — config/console (Remote Config, ad-unit IDs, flags, CMS) · backend/server · stale build/env/device · works-as-designed · duplicate · cannot-reproduce. **Cite the evidence** for the verdict (a log line, a spec statement, a code path, a ledger row).
- **A2** Not a real code bug → route to **Phase 4 Fix-9** (non-code `[VN]` comment) or defer; do NOT branch or invent a code fix to look done.
- **A3** **Duplicate check first:** read `record_bug_status.md`; a matching `root_cause_slug` (in-flight/done) → surface the duplicate + ask (`Skip`/`Fix anyway`) before deep analysis.

## 2. Reproduce first — on-device (`[REPRO]`) — **conditional on `[REPRO_ON]`**
> **`[REPRO_ON]=false` (interactive default / `--no-repro`) → SKIP A4–A6 entirely.** Jump to §5 Rigor (A11–A15) with the Fix-6 block carrying `Reproduced: skipped (no --repro)` + `not device-verified`. The analyzer does NOT acquire the device lock in Phase 3; §4 can't-reproduce ladder (A8–A10) is also skipped (nothing to ladder — no repro was attempted).
- **A4.0** **Repro runs on the BASE build, never on whatever is already installed.** First `bash <skill-dir>/assets/apk-cache.sh get <repo> origin/<BASE> <BUILD_CMD task>` — a hit is that commit's APK, already built; a miss → build `origin/<BASE>` in a temp worktree with `BUILD_CMD`, then `apk-cache.sh put` it for the next ticket — and install it with `device-lock.sh install` — a dev phone usually carries a newer build (often with the fix already in), so driving it proves nothing. Install refused (signature mismatch, downgrade) or `INSTALL_TIMEOUT` (a phone waiting on an install / Play Protect prompt) → release that serial and take the next one from `free-serial`; do not drive the old APK. Drive the device with `source <skill-dir>/assets/dev.sh <serial> <session-id>` (`tap_text`, `wait_text`, `ui`, `L`, each call bounded; `map_show` first — what earlier runs learned about this app (its local map `.jira-bug/app-map.json`: app id, screens, data states — it fills in over a few runs and is re-walked and overwritten when the app's flow changes); `nav_to <screen>` / `state <name>` to get where the bug is in one call; after reaching a screen or a data state by hand, `map_save screen|state <name> '<steps>' '<check>'` (refused unless the check holds) and put `MAP_SAVED=` in the Fix-6 Evidence field; `nav_home .jira-bug/setup.json` to reach home in one call; `NAV=no-recipe` → after reaching home by hand, `nav_save` the path and put `NAV_SAVED=` in the Fix-6 Evidence field. Never loop taps blindly: when a tap does not change the screen (`ui` shows the same texts), stop and read the screen) and take every screenshot with `assets/shot.sh` — never a hand-made adb wrapper or a bare `screencap` (an unbounded one hung AIP396-475's analysis for 15 min). (AIP396-461 A/B: the analyzer drove the phone's installed build for 4.5 min, saw the bug already fixed, then rebuilt develop and moved to the emulator.)
- **A4** **Reproduce the bug on-device BEFORE settling a root cause.** Acquire the device lock (`references/helpers/device-lock.md` — serialized, shared with Phase 5), follow the repro steps from the ticket + media, and **observe via human-mcp** (`eyes_analyze`, text back — `references/helpers/media-analysis.md`). A confirmed on-device repro is the evidence anchor.
- **A5** **Save the repro evidence** — image for a static/visual bug, screen-recording for a dynamic/flow/animation/crash bug — into `.jira-bug/evidence/<TICKET>/`, named **`repro-<what>.png|mp4`** (a case driven that did NOT trigger the bug → **`repro-attempt-<case>.…`**). This is the **"before" state Phase 5 reuses** (don't capture the bug state twice) **AND the proof posted to the ticket**.
- **A5b** **`[EVIDENCE]` The repro evidence MUST reach the Jira ticket — saving it to disk is not enough.** The analyzer is **read-only (it never posts to Jira)**, so it **returns the saved paths** in its Fix-6 `Evidence` field and the **main session posts them** the moment the analysis lands (Phase 3 — the "đã tái hiện được" comment, `jira_evidence_comment` with `EVIDENCE_CAPTION="Ảnh/Video tái hiện lỗi"`). A run that reproduced a bug on-device and left the ticket with no visible proof has failed this rule — the reporter/QA cannot tell a real confirmed bug from a guess. **A repro whose evidence was never posted is a BUG in the run, not a style preference.**
- **A6** **Trace the trigger→symptom code path** the repro exercised on the latest `origin/<BASE>` (`git grep`/`git show`, read-only). The root cause MUST connect the observed repro to a specific `file:line` — not a guess from the description.

## 3. Device policy — three branches by `[REPRO_ON]` + mode (A7)
- **A7a `[REPRO_ON]=true` + `--auto` → device HARD-REQUIRED, no static fallback.** If no device is obtainable, the lock can't be acquired within the bounded wait, or the repro ladder (§4) fails → **defer + end-of-run report** (`deferred: unreproducible`/`no-device`). `--auto --repro` NEVER auto-fixes a bug it could not reproduce on-device — this is the `[AUTO]` "confident-only, defer the rest" bar for the opt-in path.
- **A7b `[REPRO_ON]=true` + interactive → repro-first, degrade gracefully.** Device genuinely unavailable / lock busy after the bounded wait → fall back to **static evidence-based repro** (derive deterministic steps + trace the code path, §2 A6 without the device) and **flag the analysis `not device-verified`** in the Fix-6 block. The dev decides whether to proceed.
- **A7c `[REPRO_ON]=false` (interactive default / `--no-repro`) → skip A4–A6 by design.** Not a degradation path — the user did not ask for device repro. The analyzer: does NOT acquire the device lock, runs the static trace from media + code only (§2 A6 without the device), emits `Reproduced: skipped (no --repro)` + `not device-verified` in the Fix-6 block, scores `deterministic_repro=0` with `reason: no-repro-flag`. Under `--auto` the compensating control is the raised threshold (`auto-plan-pick.md` → threshold = 90 instead of 80). To opt in, pass `--repro` or use NL intent (e.g. "tái hiện trên máy", "reproduce it on device" — see SKILL.md `[REPRO]`).

## 4. Can't reproduce → candidate-cases ladder, then defer — **only when `[REPRO_ON]=true`**
> Skipped entirely when `[REPRO_ON]=false` (A7c): nothing was attempted on-device, so there is nothing to ladder. The Fix-6 block simply carries `Reproduced: skipped (no --repro)`.
- **A8** Not reproduced on the ticket's steps → **enumerate candidate trigger-cases** and drive each to try to trigger it: app state (empty / first-run / logged-out / offline) · remote-config/flag variant · timing/race (slow net, rapid taps, backgrounding) · data variant (long text, missing field, locale) · device/OS variant · build variant (release vs debug).
- **A9** A case reproduces → that's the trigger → proceed to root cause (A6) noting the exact condition.
- **A10** No case reproduces after the ladder → **defer as unreproducible; NEVER guess-fix.** Post a `[VN]` comment asking the reporter for exact steps / a video / the build + device, and move the ticket back to **Request**. **`[EVIDENCE]` ATTACH the `repro-attempt-*` media to that comment** (`jira_evidence_comment`, `EVIDENCE_CAPTION="Các trường hợp đã thử (không ra lỗi)"`) — showing exactly which cases were driven and what the screen looked like turns a vague "không tái hiện được" into something the reporter can answer in one reply ("thiếu bước X" / "phải bật cờ Y"). **Under `--auto` this comment is still posted** (it is a `[REST]` write, not an ask) alongside the `unreproducible` defer + report.

## 5. Rigor
- **A11** **One evidence-backed root cause** — every claim cites a `file:line`, log, media frame, or repro observation. Split evidence → pick the single most-likely and put the one confirming check in *Câu hỏi cần làm rõ* (never present (a)/(b)/(c) as the answer).
- **A12** **Verifiability:** the repro steps you confirmed **become the Phase-5 verify script.** If you cannot state how Phase 5 will reproduce + verify the fix, the diagnosis is not done — clarify or defer.
- **A13** **Honest scope sizing** — state the files + blast radius so the confidence scorecard and fix-vs-defer decision are grounded, not optimistic.
- **A14** **No Phase-4 handoff without a confirmed or strongly-evidenced trigger.** Hypothesis-only → clarify (Fix-7) or defer (`--auto`) — do not branch/fix.
- **A15** **Fix the reported flow; list the look-alikes.** The plan covers the flow the ticket and its media show (here the repro path) — completely, every read path of it (R24). Other flows that show the same symptom through a different source (another save path, another screen family) go under *Ngoài phạm vi* as a named follow-up, unless the very same change fixes them. Do not turn a one-flow bug into a data-model change to cover flows nobody reported: the plan gets big, scores 0 on `small_change`, and defers. (AIP396-475 A/B: three runs fixed the video-vocab flow in one file — the merged, QA-Closed fix did exactly that; one run widened it to every save path, proposed a schema change, scored 50 and deferred.)

## Scorecard link
The **`deterministic_repro`** criterion in `references/helpers/confidence-rubric.md` is scored from the A4/A8 result:
- `[REPRO_ON]=true` + reproduced on-device (A4) or via a candidate case (A9) → **full points**.
- `[REPRO_ON]=true` + not reproduced (A10) → **0** — which, with the other criteria, routes `--auto --repro` to defer.
- `[REPRO_ON]=true` + interactive `not device-verified` (A7b) → score conservatively (partial/0); the dev always still approves at Fix-8.
- `[REPRO_ON]=false` (A7c, default) → **always 0 by design**, `reason: no-repro-flag`. Not a failure. The `--auto` auto-approve threshold raises to **`AUTO_THRESHOLD_DEFAULT`** (`references/constants.md`) to compensate (`auto-plan-pick.md`).

## Analysis checklist (what "analyzed" means)
A ticket is properly analyzed only when: **reality-checked** (A1–A3) · **either** reproduced on-device (A4–A6) or run through the ladder (A8–A9) or static+flagged (A7b) **when `[REPRO_ON]=true`**, **or** static-only + `not device-verified` (A7c) **when `[REPRO_ON]=false`, DEFAULT** · **or** deferred if unreproducible (A10, only reachable under `[REPRO_ON]=true`) · with **one evidence-backed, verifiable, scoped root cause** (A11–A15). Anything short of this is not ready for Fix-8.
