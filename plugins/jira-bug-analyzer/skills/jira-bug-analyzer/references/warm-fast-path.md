# Warm fast-path (multi)

> Moved verbatim from SKILL.md in v1.15.3 (P4). SKILL.md keeps the 4 rules that must never be skipped; this file has the full directive list.

> **Warm fast-path (multi) — skip the init-file read + run env-check ∥ jira-pull.** For a multi run you MAY run `init-multi.sh "<root>" --project <KEY>` (the rule-4 command) **before** reading the phase1 init file. Then act on its emitted directives without opening the MD:
> - **`SETUP_TYPE=google-sheet` (`[SHEET]`)** → the fast-path does NOT apply (init forces `NEXT=read-phase1`, `PULL_NOW=no`). The board is a Google Sheet: read the phase1 **Pull & list** block's `[SHEET]` branch and follow `references/google-sheet-board.md` (render from the local `setup.sheet` cache, background-refresh via `assets/sheet-board.sh`). `SHEET_CSV`/`SHEET_CACHE`/`SHEET_URL` carry the sheet handle. Skip the `jira_search` bullets below.
> - **`PULL_NOW=yes` (THE bug-list speedup — applies even when `NEXT=read-phase1`)** → the cached pull needs ONLY the emitted `PULLQUERY_JQL` + `PULLQUERY_FIELDS`, so **fire `jira_search` IMMEDIATELY as your first action after init — before reading any phase/detail file** (no separate `Read` of `setup.json`). The slow network round-trip must start first. If a non-trivial state also set `NEXT=read-phase1`, **Read the phase1 detail file in the SAME message as the `jira_search` call** so the fast local read overlaps the network round-trip — **NEVER read the file first and then call Jira** (that was the old slow order). When `NEXT=pull` (all-green) you may skip the phase1 read entirely and render from the fast-path spec below. The pending-state handling (`PENDING_WATCH`/`PENDING_BATCH` hint, etc.) happens **after the list renders**, not before the pull. The list renders the instant `jira_search` returns.
> - **`NEXT=pull`** → fire `jira_search` immediately using the emitted `PULLQUERY_JQL` + `PULLQUERY_FIELDS` (no separate `Read` of `setup.json`), then render the bug list grouped by **semantic Category** (infer each bug's feature / functional area from the full summary via LLM judgment — NOT a bracket parse; the `[...]` tag is only a hint), priority-sorted, **continuous numbering across groups**, **≤4/category/turn**, and ask the dev to pick indices. **Run the categorization INLINE on the main loop — NEVER delegate it to a subagent (the skill's default model is `sonnet`, fast enough to group a short list inline); see phase1's "List the bugs grouped by category".** Do NOT read `phase1-init-multi-mode-without-team.md` — phase1 stays the **canonical** list spec for the cold path and every non-warm state.
> - **Re-pull turns (turn 2+) — fire the pull WITHOUT waiting for the init script.** The moment you've already emitted `PULLQUERY_JQL` once this session, a re-pull (phase3 turn-loop step 1/11) fires `jira_search` from that **in-context JQL immediately** — in the **same message** you (re)run `init-multi.sh … --project <KEY>` in the **background** (`run_in_background: true`) for env/memory revalidation. Do NOT block the re-pull on the script. Reconcile only if that background init later reports a changed `BOARD`/`PULLQUERY_JQL` (re-fire) or `ENV=block:<dep>` (handle the block). Turn 1 still needs the foreground script for the JQL.
> - **`NEXT=read-phase1`** → use the phase1 init file's INIT-STATUS table for the non-trivial state. **But if `PULL_NOW=yes`, the `jira_search` pull still fires FIRST** (see the `PULL_NOW` bullet): read the phase1 file in the **same message** as the pull — concurrently, never before it. Only when `PULL_NOW=no` (no cached query) do you open phase1 before any Jira call.
> - **`BASEBRANCH=<branch>`** → the persisted integration branch (e.g. `develop`) for every worktree + PR (`<BASE>`); carry it forward, no prompt. **`BASEBRANCH=none`** → the local setup doesn't carry it (new, predates the field, or the dev removed it). init **never auto-fills it** and forces `NEXT=read-phase1`. **You MUST `AskUserQuestion` for the base branch IN THIS INIT TURN — render the bug list first, then ask in the same turn. Do NOT defer the ask to fix time and do NOT resolve it silently, even if CLAUDE.md states a branch "confidently"** (that value is only the prompt's recommended default = `BASEBRANCH_SUGGEST` if emitted, else resolved per the Base branch block in `references/run-blocks.md`). On the dev's pick, persist to **BOTH** layers — local `.jira-bug/setup.json` **AND** the shared `project/<KEY>/setup.json` (push via `memory-keeper`/`memory-sync.sh push`) in the **same turn**; the shared push is **mandatory, not deferred** (local-only = the next dev gets re-asked). Never branch from a hardcoded `origin/main`. This is a hard gate — see the `BASEBRANCH=none` row in the phase1 file + the Base branch block.
> - **⚠️ Phase 2 §2.0 discovery STILL RUNS on the fast path — it is not in the skipped phase1 file.** The `NEXT=pull` bullet tells you to skip `phase1-init-multi-mode-without-team.md`, and that file is where the "after the pick → run Phase 2 §2.0" pointer lives. **Skipping phase1 must NOT swallow Phase 2.** After the pick (or the `--auto` auto-pick), go to `references/helpers/source-of-truth-discovery.md` and resolve spec/figma **before** claim/analyze — on EVERY warm turn of a phase whose `sotByPhase[<PHASE>]` is not already populated. Jumping pick → claim → analyze on the fast path is the known bug this bullet exists to prevent.
> - **`REFRESH≠none`** (`env`/`memory`/`env,memory`) → **LIST FIRST, refresh after.** The moment `jira_search` returns, **render the bug list as the FIRST thing in that turn** — the list text comes before any refresh activity. Then, in the **same message, AFTER the rendered list**, spawn ONE **background** subagent (haiku, `run_in_background: true`) running `init-multi.sh "<root>" --project <KEY> --env-refresh` (env+mcp probe + memory pull, **off the critical path**). Do NOT couple the refresh spawn to the `jira_search` call and do NOT spawn it before the list — the dev must see the board first, never a "Async agent launched" line ahead of it. **NEVER wait for the subagent's completion notification before (or after) listing.** Its output is consumed lazily, long after the list is shown: a `memory` refresh is only read at the later dedup/claim gate; an `ENV=block:<dep>` is handled when its notification arrives (or at the next gate that needs the dep) — neither gates the list. The refresh starting one turn later than the jira call is harmless — it is only needed many turns on at claim time.
